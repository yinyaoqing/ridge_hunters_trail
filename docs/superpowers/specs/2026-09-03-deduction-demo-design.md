# Ridge Hunter's Trail — 推理說明與示範 v1.0

> 現況：說明頁 13 列全部在「告訴你」——足跡是錐形、氣味是環帶、圖層依符合數上色——
> 但沒有任何一處「示範」兩條線索疊起來會發生什麼。實戰引導 `tut.move / tut.read /
> tut.cross / tut.qte` 只有四行字，`tut.cross` 雖會把交集格閃 1.5 秒，卻是在一張同時要
> 應付迷霧、地形成本、體力的真實地圖上。
>
> 本文件設計一個獨立的互動示範場景：用一個乾淨、固定、數學已驗證的小關卡，
> 把整套推理流程走一遍。範圍不含遊戲規則改動——這是純粹的教學層。

---

## 1. 決策紀錄

四個分歧點由 owner 裁定：

| 分歧 | 裁定 | 落選項與理由 |
|---|---|---|
| 形式 | **獨立互動示範場景** | 說明頁靜態圖解太弱；在真實第 1 局疊圖則要與迷霧／地形／體力搶注意力 |
| 範圍 | **全套**（交集、幌子、標記、眺望） | 只教交集會漏掉第 4 局之後真正的難點 |
| 入口 | **三處**：說明頁、營地、失敗結算 | 首次遊玩不強制進入，維持現有彈窗流程 |
| 互動度 | **看為主，三個動手點** | 純簡報容易被快速點完且毫無記憶；全程可玩等於重跑一次 MapScene |

## 2. 架構

### 2.1 分層

```
src/core/demo.ts      課程內容（純資料 + 驗證函式）  ← 可單元測試
src/scenes/DemoScene.ts  薄渲染層（重用 paint.ts / palette / fx）  ← 只能 build + 冒煙
```

課程內容進 `core` 不只是分層潔癖。**這套課程有可驗證的真值**：交集真的是 11 格嗎？
幌子真的和兩條真線索都不相交嗎？押注步驟的正解真的唯一嗎？放進 `core` 這些全部測得到；
放進場景就只能靠人眼。本專案 `vite.config.ts` 的 `test.environment` 為 `node`，
Phaser 場景無法單元測試——把可驗證的部分擠出場景，是這個限制下唯一能提高信心的手段。

考慮過但否決的兩種做法：

- **場景內硬寫 `switch (step)`**：少一個檔案，但把整套課程塞進唯一不可測的那一層，
  且會重演 MapScene 膨脹到 1476 行的老路。
- **用固定種子跑真實 session**：最「真」，但示範需要的正是乾淨可控的畫面；
  更關鍵的是固定種子的產物會隨 `generate.ts` 任何改動而漂移，課程隨時可能無聲講錯。

### 2.2 `src/core/demo.ts` 對外介面

```ts
export const DEMO_SIZE = 9;
export const DEMO_START: Vec2;      // 玩家起點
export const DEMO_TARGET: Vec2;     // 真實位置
export const DEMO_CLUES: Clue[];    // 4 條，索引固定，其中 1 條 isDecoy

export type DemoAction = 'exclude' | 'mute' | 'wager';

export interface DemoStep {
  chapter: 1 | 2 | 3 | 4;
  narration: MsgKey;              // 旁白
  vars?: Record<string, number>;  // 旁白裡的數字，由 candidates()/intersect() 於模組載入時算出
  clues: number[];                // 本步已判讀的線索索引
  muted: number[];                // 本步已靜音的線索索引
  overlay: 'none' | 'heat' | 'intersect';
  seen: 'near' | 'all';           // 迷霧狀態
  player: Vec2;                   // 玩家位置（第四章會移動）
  autoSuspect?: true;             // 為真時，11 格交集自動標成存疑
  action?: DemoAction;            // 有值時，此步必須玩家動手才能前進
}

export const DEMO_STEPS: DemoStep[];   // 14 步

// 動手點的驗證：回傳 null 表示接受，否則回傳該顯示的提示 MsgKey。
// 拆成兩個函式而非一個吃 `Vec2 | number` 的聯集——格子動作與線索動作
// 本來就是不同的東西，讓型別替呼叫端擋掉傳錯的參數。
export function checkCellAction(action: 'exclude' | 'wager', cell: Vec2): MsgKey | null;
export function checkMuteAction(clueIndex: number): MsgKey | null;
```

`vars` 是刻意的設計：旁白裡的「81 剩 33」「只有 11 格」全部由 `candidates()` / `intersect()`
算出後帶入 `{n}`，一個都不寫死成常數；並有一條測試斷言每一步的 `{n}` 佔位符與它是否提供
`vars` 恰好對稱。如此文案與畫面**在結構上不可能對不上**。

### 2.3 渲染層

`DemoScene` 沿用 `HelpScene` 已驗證的並行疊層模式：`scene.pause()` 呼叫端 +
`scene.launch('Demo', { from })`，關閉時 `scene.stop()` + `scene.resume(from)`。
繪圖一律重用既有函式（`drawClueToken`、`dashedCircle`、`dashedArc`、`getPalette`），
確保示範看到的圖形與真實地圖**逐像素同一套語彙**——這是教學能遷移的前提。

## 3. 示範關卡

9×9，81 格。玩家起點 `(1,8)`，目標 `(6,2)`。

| # | 線索 | 位置 | 參數 | 候選格 |
|---|---|---|---|---|
| 0 | 足跡 | `(2,7)` | 方向 309°、錐半角 25° | 33 |
| 1 | 氣味 | `(8,8)` | 距離 6、容差 0.75 | 15 |
| 2 | 足跡（**幌子**） | `(3,4)` | 方向 225°、錐半角 25° | 9 |
| 3 | 擾動 | `(6,0)` | 半徑 2 | — |

參數全部落在 `getDifficulty()` 實際使用的區間內（錐半角 15–40、氣味容差 0.5–1.0、
擾動半徑 2–4、氣味距離為整數）。這不是為了教學捏造的特例，玩家在真實關卡會遇到同一種東西。

### 3.1 已驗證的數學性質

以真實的 `candidates()` / `intersect()` / `heatMap()` 實測：

- 線索 0 ∩ 線索 1 = **11 格**
- 幌子（線索 2）與線索 0、線索 1 **皆完全不相交**
  → 三條全開時最高符合數為 2，且符合 2 條的格子恰好就是那 11 格
  → 「兩條互相印證、一條落單」在圖層上字面成立，不是修辭
- 線索 0 ∩ 線索 1 ∩ 線索 3 = **恰好 1 格**，即 `(6,2)`
  → 掃過全部 81 個位置 × 半徑 {2,3} 的組合，**這是唯一解**

這三條性質是課程的地基，全部進 `tests/demo.test.ts` 釘死。

### 3.2 迷霧

示範不重現 `vision.ts` 的視野規則——那是 `help.vision` 的職責，在這裡只會分散注意力。
迷霧在此只需成立一件事：**第四條線索藏在你看不見的地方**。因此直接以最上面兩列為未探索區：
它剛好涵蓋線索 3 的 `(6,0)`，且完全不觸及 11 格交集區（其最小 y 為 2）。
第 11 步眺望後全圖可見。

## 4. 十四步腳本

### 第一章　一條線索只會排除，不會指認

| 步 | 內容 | 動手 |
|---|---|---|
| 1 | 空地圖，玩家在左下，一枚足跡記號；右上一片未探索暗區。「81 格，牠在其中一格。線索不會直接告訴你是哪一格。」 | — |
| 2 | 判讀足跡 → 錐形亮起。「足跡朝東北——牠在這片錐形裡。81 剩 33。」 | — |
| 3 | 「錐形外的 48 格都不可能。挑一格排除掉。」 | **①排除** |

動手 ① 驗證：點錐形外 → 接受，該格畫紅 ✕；點錐形內 → 提示「這格還在可能範圍內」。

### 第二章　交集才是答案

| 步 | 內容 | 動手 |
|---|---|---|
| 4 | 氣味線索 → 環帶亮起。「牠離這裡六格遠。」 | — |
| 5 | 疊圖，圖層依符合數上色，11 格最亮並自動標成存疑黃圈。「兩條都符合的只有 11 格——這就是 HUD『圖層』在做的事。」 | — |

### 第三章　落單的那條在說謊

| 步 | 內容 | 動手 |
|---|---|---|
| 6 | 第三枚足跡（朝左上）→ 第三個錐形亮起 | — |
| 7 | 「三條的交集是空的。不可能三條同時為真。」 | — |
| 8 | 「看符合數：11 格符合兩條，沒有一格符合三條。兩條互相印證，一條和誰都對不上。」 | — |
| 9 | 「把說謊的那條靜音。」 | **②靜音** |

動手 ② 驗證：點線索 2 的記號 → 接受，記號轉灰、圖層回到 11 格；
點線索 0 或 1 → 提示「這條和另一條吻合，再看看哪條落單」。

### 第四章　眺望，然後押注

| 步 | 內容 | 動手 |
|---|---|---|
| 10 | 「11 格還是太多，而遠處你看不見。」玩家往交集區移動 | — |
| 11 | 眺望環掃過，迷霧退開，右上角露出第四條線索。「眺望不只找線索，也讓你看得見地。」 | — |
| 12 | 判讀擾動 → 交集收斂到 1 格 | — |
| 13 | 「就是這裡。把它押注下去。」 | **③押注** |
| 14 | 揭曉：牠在這裡。「讀、疊、剔、望、押——每一局都是這五件事。」 | — |

動手 ③ 驗證：點 `(6,2)` → 接受，前進到第 14 步畫出金色雙環與揭曉；
點其他格 → 提示該格不符合全部三條線索。

揭曉獨立成第 14 步，而不是塞進第 13 步的動作回呼裡：**每一步恰好對應一個顯示狀態**，
渲染因此可以是 `render(stepIndex)` 的純函式，上一步／下一步不會累積狀態漂移。

### 4.1 為什麼是這三個動手點

它們各自對應遊戲裡**最容易被完全錯過的功能**：排除標記、線索靜音、押注。
靜音尤其——它目前只存在於說明頁 `help.layer` 的半句話裡，沒人教就永遠不會有人用。

## 5. 入口與返回

| 來處 | 位置 | 條件 |
|---|---|---|
| `Help` | 標題下方一顆主鈕 | 永遠顯示。Help 先 `scene.stop()` 自關，再 launch Demo，並把自己的 `from` 傳下去，回程直接回到 Map/Camp |
| `Camp` | 工具列 `?` 旁 | 永遠顯示 |
| `Result` | 主線失敗分支，主鈕上方的文字連結 | 玩家剛失敗、最想知道「我到底該怎麼想」的那一刻。**每日挑戰失敗分支刻意不接**——該分支的垂直預算已被連勝列＋重試鈕＋返回營地鈕佔滿（座標一路夾限到 `h - 30`），硬塞第三個元素會重演 F7 的重疊問題；每日挑戰玩家仍可從營地與說明頁進入 |

首次遊玩維持現狀（`rht.help.v1` 控制的說明頁自動彈出），不強迫任何人上課。

## 6. 測試策略

`tests/demo.test.ts` 釘住課程的真值，而非渲染：

1. 目標格同時符合三條真線索；幌子不涵蓋目標格
2. 幌子與兩條真線索皆不相交（第三章的推理成立）
3. 線索 0 ∩ 線索 1 的大小 == 旁白帶入的數字（`narrationVars` 與 `intersect()` 同源）
4. 三條真線索交集恰為 `{DEMO_TARGET}`（第四章的收斂成立）
5. 三個動手點：正解通過、反例被拒（每點至少一個反例）
6. `DEMO_STEPS` 恰為 14 步，結構完整：章節單調遞增、`clues`／`muted` 索引合法、
   `muted` ⊆ `clues`、有 `action` 的步驟其型別可被對應的檢查函式處理
7. 迷霧涵蓋線索 3 的位置，且不觸及 11 格交集區（第四章的「看不見」成立）
8. **每個 MsgKey 在 `en` 與 `zh-TW` 都存在**——Phase 4 出過孤兒 key，這條直接堵死

場景層一如既往由 `npm run build`（`tsc --noEmit && vite build`）加人工冒煙把關。

## 8. 明確不做

- 不動任何遊戲規則、難度參數或 `generate.ts`
- 不改現有 `tut.*` 四步實戰引導——它與示範互補，不是替代
- 不做進度記憶（看到第幾步）。14 步的東西不值得一個 localStorage key 與它的降級路徑
- 不做語音、不做動畫分鏡以外的演出

## 9. 風險

**最大風險是沒人點進來。** 三處入口是對策，但若實測顯示轉換率低，
下一步是把失敗畫面那顆改成自動提示（而非把它塞進首次遊玩流程——
把 14 步的課堵在遊戲最前面會勸退隨手點進來的人）。

次要風險：新增約 300–400 行的場景，且與 Phase 4／Phase 5 一樣**無法單元測試**。
本專案目前已累積兩期未經瀏覽器實測的視覺改動，本階段會再疊一層。
建議在實作計畫的最後一項明確要求人工冒煙，且與前兩期的補測合併進行。
